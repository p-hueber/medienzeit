# Handoff: styling the Medienzeit admin page

## What this is

Medienzeit is a screen-time system for one child's two devices, an Android phone and an
iPad. A small ESP32 board sits in the room with an e-ink display and an NFC reader. Each
device carries an NFC sticker; putting a device back at the reader stops its clock, taking
it away starts it. When the shared budget runs out — or during the night window — the
FRITZ!Box cuts that device off the internet.

**The admin page is the parent's control surface.** It is served by the board itself over
plain HTTP on the LAN at `http://medienzeit.fritz.box`, behind HTTP Basic auth.

It is not a dashboard anybody browses for pleasure. It gets opened in two situations, and
the design should serve both:

1. **In a hurry, mid-negotiation.** "I need ten more minutes for homework." One-handed, on
   a phone, possibly with a child watching. The bonus buttons must be unmissable and hard
   to mis-tap.
2. **Occasionally and deliberately.** Adjusting the rules — how fast time accrues, how
   much can bank up, when night starts. Rare, considered, and worth getting right.

There is a third job the page does quietly: **showing that alerting still works.** Push
alerts are how the parent learns about a device taken at night or used off-network. A
silently dead alert channel looks exactly like a fortnight of good behaviour, so its
health is on the page deliberately.

## Hard constraints

These are not preferences. Breaking any of them means the page does not render.

**No external resources of any kind.** No CDN, no web fonts, no Google Fonts, no external
images, no analytics. The board serves everything itself, has no TLS, and the LAN may have
no internet at all. Everything must be inline or served from the device.

**No build step, no framework.** The HTML is generated by Rust `write!` calls into a fixed
buffer. There is no bundler, no preprocessor, no npm. Deliver plain CSS.

**Minimal JavaScript, ideally none.** The page works today with zero JS. Small vanilla
enhancements are acceptable if the page still works fully without them; anything requiring
a framework is out.

**Byte budget** — the important one, explained below.

## The byte budget, and how to get more

Today the whole page is **1850 bytes**, generated per request into a `heapless::String<3072>`
before being copied into a `String<4096>` with the HTTP headers.

So as it stands there is only about **1.2 KB of headroom** — not enough for elaborate CSS.

But that limit is an artefact of how the page is assembled, not a real one:

- **Flash is abundant**: ~2.3 MB free of a 3 MB app partition. A `const &str` stylesheet
  costs flash, not RAM, and 20–30 KB of CSS is nothing.
- **RAM is the constraint**, because the generated HTML accumulates in that buffer.

**The recommended fix, which the firmware side will implement:** serve the stylesheet from
its own route (`GET /s.css`) as a `const &str` written straight to the socket, never
through the page buffer, with a long `Cache-Control`. The HTML then keeps only a
`<link rel=stylesheet href=/s.css>` and stays small.

**So: assume roughly 16 KB of CSS is available**, and ask if you need materially more.
State what you need and it can be arranged — this is a budget to design within, not a
cliff to fear. Inline `<style>` is the thing to avoid, because that *does* come out of the
1.2 KB.

## Audience, device, context

- **Phone first.** A parent's phone is where this gets opened. Desktop should be fine but
  is not the priority.
- **Touch targets matter more than density.** The bonus buttons especially — a mis-tap
  grants time that cannot be un-granted from this page.
- **Dark mode is worth having.** A likely moment for opening this page is 22:40, in a dark
  hallway, having just been alerted that a device was taken at night. Respect
  `prefers-color-scheme`.
- **One user.** No multi-user states, no onboarding, no empty states beyond "starting up".

## Content inventory

The rendered page (see `docs/admin-page-current.html` for a live capture) contains, in order:

| Block | Content | Notes |
|---|---|---|
| Balance | `NNN min`, currently a 3 rem bold number | The single most important number on the page |
| Status table | Status (charging / running / held), local time, night yes/no, per-device state | Two devices, each "put back / taken away" and "allowed / blocked" |
| Alert health | One line, red when failing | Must be conspicuous when failing, quiet when fine |
| Grant confirmation | Appears after granting | Explains the number above is momentarily stale |
| Bonus buttons | `+10 min`, `+30 min` | The hurried path. Make these obvious |
| Rules form | 8 inputs + save button | The deliberate path. Fine to be visually secondary |
| Rules explainer | One paragraph of small grey text | Explains that changes are immediate and persistent |

### The rules form fields

| Label | Input | Meaning |
|---|---|---|
| Earn | two numbers: `N` per `M` min away | The refill ratio, default 1 per 10 |
| Most it can hold | minutes | Cap, default 180 |
| Debt allowed | minutes | How far below zero the balance may go, default 30 |
| Fresh start | minutes | Prefill on a blank device, default 60 |
| Free pickup | seconds | Grace before a pickup is billed, default 180 |
| Night from / until | `<input type=time>` ×2 | Default 21:00 / 06:30 |

The "Earn" row is two inputs in one sentence and is the awkward one to lay out.

## Language

The page is currently in English; the e-ink display and the push alerts are in German. The
household is German-speaking, so **German is the better target** for consistency — but
confirm before translating, since it is a product decision rather than a styling one.

One fixed term if you do translate: a device at the reader is **"zurückgelegt"** (put
back). That word was chosen deliberately and should not be substituted.

Note also that the physical installation has no enclosure and no decided location. Avoid
copy or iconography implying a box, dock, cradle, or station.

## Tone

The system's design principle throughout is **detection over prevention**: it does not
pretend to be unbeatable, it makes the honest path frictionless and makes anomalies
visible. The page should feel like an honest instrument — calm, factual, not gamified, not
punitive, and not cute. It is read by a parent, but it concerns a child, and it should not
feel like a surveillance console.

## What is fixed vs free

**Fixed** (firmware-side, changing these means changing Rust):

- The set of fields and their semantics
- Form submission is a plain `POST` to `/` with `application/x-www-form-urlencoded`
- Field `name` attributes: `grant`, `rn`, `rd`, `cap`, `floor`, `pre`, `grace`, `ns`, `ne`
- Basic auth, so no login UI

**Free** (yours):

- All layout, typography, colour, spacing
- Markup structure and class names — say what you want and the generator will emit it
- Grouping, ordering within reason, progressive disclosure of the rules form
- Whether the status table stays a table

## Deliverable

1. **`s.css`** — the stylesheet, plain CSS, no imports.
2. **A sample `index.html`** showing the markup the CSS expects, with realistic values, so
   the Rust generator can be written against it. Static and openable in a browser.
3. **A note of any markup changes** you need from the generator.
4. **The rendered byte size** of your CSS.

Both light and dark should be demonstrated.

## Testing it

The simplest loop is to open your sample HTML directly in a browser — it is static and
self-contained. Against the real device: `http://medienzeit.fritz.box` with the credentials
in `firmware/web.toml` (gitignored, not in this repo).

## What not to do

- Do not add tracking, telemetry, or any outbound request.
- Do not add a framework, a build step, or a package manager.
- Do not make the bonus buttons smaller or more decorative than the rules form. The
  hurried path is the important one.
- Do not represent the child's usage as a score, streak, or leaderboard. It is a budget,
  not a game.
